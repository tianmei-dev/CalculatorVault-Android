# 隐私合规与代码一致性核查（2026-10-28）

## 结论与边界

当前版本存在明确的告知与实现不一致，不宜标记为“隐私合规核查通过”。本次为代码、打包配置及文档一致性核查，不是法律认证，也未进行真机抓包或 SDK 动态隐私检测。

核查基线：当前 main 工作区，包括用户尚未提交的四份配套文档修改。四份文件指 children_privacy_policy、permission_description、personal_information_list、third_party_sdk_list。未修改这些文件、主政策或业务代码；仅新增本报告及依赖核对日志。

## 已确认问题（按优先级）

### P1：首次同意页仍有与真实功能相反的告知

`app/src/main/res/values/strings.xml:11` 的 privacy_local_note 写“不收集您的账号”“功能数据仅保存在设备本地”，还写同意前“不收集任何个人信息”。

实际已实现微信 code 提交、服务端账号和会话；设备试用上传虽默认关闭，但已具备联网能力；Application 在同意前即记录本地首次打开时间和试用状态。主政策二-4、二-5 已披露这两类行为。用户在最关键的首次同意界面看到的是另一套说法。

建议改成具体的本地/联网分类：未同意不初始化统计/异常 SDK、不上传设备标识；本地记录首次打开和试用计时；用户主动微信登录时联网处理账号。避免“任何信息均不处理”等绝对承诺。

### P1：政策更新没有版本检查与重新同意机制

主政策及四文件日期均为 2026-10-27，主政策九承诺重大变化显著告知并在需要时重新取得同意。代码 `OnboardingRepository.kt:120` 仍写 PRIVACY_VERSION="1.0"；StartupDestinationResolver 仅看 privacyAccepted，Application.hasPrivacyConsent、友盟和 Bugly 初始化也仅检查此布尔值，未比较已同意政策版本。

因此，曾同意旧政策的用户不会因这次新增账号/试用说明自动重新看到同意页；若之后打开 TRIAL_DEVICE_UPLOAD_ENABLED，也会沿用旧同意记录读取/上传 SSAID。当前开关 false 降低了试用上传风险，但不修复版本门禁。

建议建立统一的当前政策版本及有效同意判定，SDK、试用、微信与入口守卫统一复用；对本次实质变更设计重新告知/同意迁移，并保留拒绝路径。是否需要何种同意方式应由合规负责人结合实际处理确认。

### P2：无障碍服务文档与当前安装包不一致

主政策第 50、52、170 行、权限说明第 56～78 行、收集清单第 59 行及儿童规则第 150 行描述无障碍用途或关闭入口。

全量检索未发现 AccessibilityService 子类、无障碍服务 XML、BIND_ACCESSIBILITY_SERVICE、AccessibilityEvent 处理或 rootInActiveWindow 调用；最终 Release Manifest 也没有无障碍服务。实际应用锁是 UsageStatsForegroundAppDetector + AppLockMonitorService + 悬浮窗。

**当前不存在可以核查的“无障碍读取范围”，不能把文档里的“不读取聊天/密码”当作已验证的无障碍实现结论。** 现有实现每 250ms 轮询最近 5 秒 UsageEvents，读取前后台事件类型/包名；回退 queryUsageStats 读取 lastTimeUsed 后选择最近使用的包。系统结果并非只限于用户保护列表，随后业务再判断目标是否受保护；未发现读取 UI 文本、键盘输入或屏幕内容的业务代码。

建议当前文档明确“本版本使用使用情况访问和悬浮窗，未接入无障碍”，将使用情况访问从模糊的辅助/可选描述改成当前真实用途；未来若接无障碍需另查 eventTypes、packageNames、canRetrieveWindowContent、窗口标志、节点/事件文本与截屏/手势能力。

### P2：最终 Manifest 有 SDK 合入权限，权限清单未覆盖

最终 Release 权限如下：

- INTERNET、ACCESS_NETWORK_STATE、ACCESS_WIFI_STATE。
- PACKAGE_USAGE_STATS、SYSTEM_ALERT_WINDOW。
- FOREGROUND_SERVICE、FOREGROUND_SERVICE_SPECIAL_USE、POST_NOTIFICATIONS。
- WRITE_EXTERNAL_STORAGE（maxSdkVersion=29）。
- com.google.android.gms.permission.AD_ID。
- freemme.permission.msa。
- 应用自己的 DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION（signature，AndroidX 内部动态广播保护）。

AD_ID 和 freemme.permission.msa 均来自 com.umeng.umsdk:common:9.9.8，来源可在 manifest-merger-release-report 第 499～506 行核对。配套权限说明未列出这两项；前台服务说明也未明确列出实际 specialUse 类型及两项 FGS 权限名。

建议先确认 SDK 对广告/厂商标识能力的必要性和实际调用；不必要则经功能验证后移除合并权限，必要则准确披露 SDK 处理目的和触发条件。不能仅据权限存在断言已经读取广告 ID，也不能仅因主 Manifest 没写就认为最终包没有它。

没有发现位置、摄像头、麦克风、通讯录、短信、通话记录、READ_PHONE_STATE、QUERY_ALL_PACKAGES、广泛照片读取或无障碍权限。旧系统写权限只在媒体恢复相关路径触发；应用列表由 MAIN/LAUNCHER 查询，另有微信包可见性查询。Release allowBackup=false、usesCleartextTraffic=false。

不能仅凭这些文字认定已有有效监护人同意流程。需确认儿童使用策略、适用场景和实际措施，再决定实现或文案调整；本次不直接作法律定性，也不建议为此随意新增身份证等过度信息收集。

## 首次同意和 Android ID 上传：已核实的保护措施

1. 新安装默认 privacyAccepted=false；用户主动点击同意并完成持久化后，才通知 ThirdPartySdkInitializer 初始化。拒绝入口存在。
2. 友盟、Bugly 均在初始化前读取同意状态；失败不初始化。Bugly 还检查服务标识，关闭自定义日志上传和 UserInfo；业务统计事件只传事件 ID。
3. 微信 SDK 构造不立即 createWXAPI；准备/授权由用户主动登录和隐私检查路径触发，回调也检查同意；SDK 日志采用静默实现。
4. 试用本地 initialize 不调用 DeviceIdentityProvider。sync 中先检查上传开关和 consent，之后才读取 ANDROID_ID，再调用 /trial/device/activate；处理响应前再次检查同意。标识缺失/异常安全降级。
5. TRIAL_DEVICE_UPLOAD_ENABLED 默认 false；没有因更新政策自动开启。该开关只约束**本应用自有试用接口**，不限制已获同意后的友盟 SDK 自行处理标识。
6. 自有试用请求只有 deviceKey，无 Bearer/微信 code/媒体/PIN；原始 SSAID 不落普通 SharedPreferences，不用于登录身份。业务代码未发现完整 ID 日志。
7. 撤回隐私会持久化选择、停用统计/异常 SDK、取消微信授权、退出账号并锁定隐私空间，要求进程替换；试用本地计时不重置。已在网络上传输的请求不能因撤回而追回，不能宣称撤回瞬间所有在途通信均不存在。

这些是静态路径结论，不替代 SDK 自启动、缓存上报、厂商标识读取和所有线程竞态的动态检测。
